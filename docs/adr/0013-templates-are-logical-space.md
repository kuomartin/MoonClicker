# ADR-0013：模板圖是邏輯空間的產物

**狀態**：已採納

## 脈絡

[ADR-0012](0012-surface-size-is-owned-not-derived.md) 與 CONTEXT.md 的「Surface 空間 / 邏輯
空間」把兩個座標系分清楚了：影格在 surface 空間，對外座標在邏輯空間，`VisionMatcher` 負責
轉換。`docs/lua-api.md` 據此對腳本作者承諾：

> 影格其實在 surface 空間，但轉換在引擎內部完成，腳本不需要知道它存在

座標確實做到了。`vision.*` 回傳的 `x/y/cx/cy` 是邏輯座標，`roi` 也吃邏輯座標。

**但模板圖不是。** `matchTemplate` 跑在未經旋轉的影格上，而顯示器轉 90/270 時內容是被轉
「進」緩衝區的——`TM_CCOEFF_NORMED` 不是旋轉不變的。所以直立時截的模板在橫向比不中，
腳本作者被迫為每個方向各準備一張圖，而那張圖的方向是 surface 空間的、不是他在畫面上看到
的。承諾有個洞。

這個洞一直沒被發現，因為旋轉下的比對從來沒有測試覆蓋。今天補上時才浮現：`Tier1SpikeTest`
的 step7/8 原本用旋轉對稱的圖樣（為了單獨驗證座標換算），而對稱圖樣對方向完全盲目。

## 決定

**模板圖是邏輯空間的產物：腳本作者提供的就是他在畫面上看到的方向。** 引擎負責把它轉到影格
的方向再比對。

這是對外契約，不是實作細節。它讓 `docs/lua-api.md` 那句承諾變成真話：對腳本而言，surface
空間完全不存在——座標、`roi`、模板，三者都在邏輯空間。

無條件，不提供逃生門。加一個 `rotate = false` 等於把這個洩漏永久化，而且沒有人能依賴舊
行為：旋轉這條路今天才第一次有測試。

## 目前的實作機制（不凍結）

`VisionMatcher::templateFor()` 依當前 rotation 旋轉模板，快取鍵含 rotation。方向取自
`frameToLogical` 的逆：r=1 時它把影格右上角映到邏輯左上角，即影格內容是邏輯內容順時針轉
90 度，所以模板順時針轉。

**轉影格是等價的替代方案，被排除但沒有被否定。** 「把模板轉 R 度去比未旋轉的影格」與「把
影格轉 −R 度去比原模板」在數學上是同一件事，命中位置一一對應。選轉模板的理由純粹是成本：

|  | 尺寸 | 次數 |
|---|---|---|
| 轉模板 | 一兩百像素 | 一次，`templateFor` 有跨呼叫快取 |
| 轉影格 | 720×1280 RGBA ≈ 3.5 MB | 每次比對，影格每張都是新的，快取不了 |

成本會隨硬體、影像尺寸、比對頻率而變。若哪天轉影格反而划算（例如比對頻率極低、或影格本來
就要為別的用途轉一次），換過去**不違反這份 ADR**——契約沒變，只是換了實作。

## 不在 `GlesDistributor` 轉

曾考慮在分發器就把來源轉正，讓所有消費者都拿到邏輯方向的影格。排除，理由有三：

1. **它是扇出點。** 今天的消費者除了腳本的 `NativeImageReader`，還有
   `FullscreenDisplayActivity` 的鏡像——而鏡像**已經自己在反旋轉**
   （`Viewport.viewRotationDegrees = -(quarterTurns * 90f)`，並互換 `unrotatedWidth/Height`）。
   先轉會讓鏡像轉兩次。
2. **輸出尺寸得隨旋轉改變**（720×1280 ↔ 1280×720），連帶 `NativeImageReader` 要在執行中
   重新配置緩衝區。
3. **與 ADR-0012 衝突。** 那份 ADR 的前提是 surface 尺寸是一個被擁有的常數；分發器輸出變成
   動態尺寸之後，`getDisplaySurfaceSize` 的意義就沒了。

## 後果

- 腳本作者為一個固定像素的目標只需要準備**一張**模板，任何方向都能比中。
- 尺度**仍然不是**不變的。`scale` 參數是把影格與模板一起縮小來省時間，不是拿來配不同大小
  的目標。內容若在不同方向被重新排版成不同像素尺寸（例如響應式網頁），這份 ADR 幫不上忙
  ——那是另一個問題，需要的是別的比對方式。
- 模板快取的條目數最多乘以 4。可忽略。
- `Tier1SpikeTest` 必須同時保留**旋轉對稱**與**不對稱**兩個圖樣：前者單獨驗座標換算，
  後者驗方向。少了後者，把旋轉方向寫反不會有任何測試失敗。
