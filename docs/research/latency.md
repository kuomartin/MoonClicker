# 延遲量測：template matching、OCR、GLES/H.264 管線（issue #133）

研究日期 2026-10-08。裝置為 Galaxy A21s（Exynos 850，Android 12，USB adb）與 Pixel 7a（Tensor G2，API 37，Wi-Fi adb）。量測程式與原始紀錄在 `spike/latency` 分支（`LatencyBenchTest`、`tools/latency/`），不進 master：`VisionMatcher`、`Ocr`、`GlesDistributor`、`H264EncoderSink` 的各階段以 `steady_clock`／`System.nanoTime` 計時，寫入 logcat 與測試 app 的 `files/lat.log`。Pixel 7a 的 logcat 在高頻輸出時會掉行（80 行只留下 38 行），表中數字一律取自檔案。腳本跑在 Tier 1 測試環境（測試行程內的 `MoonClickerService` 與 puppet），與 App 內執行是同一套引擎與 distributor。

除特別註明，數字為中位數（p50）／p90，單位 ms。template matching 每組 3 輪 × 5 次；其他項目 1 輪。

---

## 結論

1. **GLES distributor 的空轉是最大的浪費，而且會被下游放大。** 只要有任何 sink（vision 的影格讀取、H.264 編碼器），distributor 就以每 10 ms 一次的逾時輪詢，每秒約 82–85 次 `updateTexImage` 並重畫；畫面靜止時其中 99% 以上是同一張影格。每次重畫都會讓 ImageReader 與編碼器收到一張「新」影格：
   - 畫面靜止、`vision.wait` 設 `step_ms = 1000` 時，行程仍佔 52%（Pixel 7a）／57%（A21s）CPU。
   - 不設 `step_ms` 的 `vision.wait` 把每次重畫都當成新影格比對：A21s 在 20 秒內比對 770 次，行程 CPU 263%；Pixel 7a 236%。
   - H.264 編碼器設定 30 fps，實際收到 87 fps（Pixel 7a）／71 fps（A21s），位元率因此是設定值的 2–4 倍（Pixel 7a 鏡像實體螢幕時約 7.8 Mbps，設定 2 Mbps）。
2. **template matching 的耗時由搜尋區域大小與色彩決定，與模板大小幾乎無關。** 彩色比對是灰階的 3–4 倍。A21s 上 720×1280 全畫面彩色約 1 秒、1080×2400 約 3–4 秒；Pixel 7a 分別約 130 ms 與 440 ms。把搜尋範圍限定在 1/8 畫面的 ROI 是最有效的加速：A21s 降到約 100 ms，Pixel 7a 約 15 ms。
3. **OCR 在引擎內的耗時與選型研究一致。** ROI 讀數（`vision.read`）A21s 122 ms、Pixel 7a 19 ms；720×1280 整張辨識 A21s 約 1.6 秒、Pixel 7a 約 0.34 秒。
4. **影格本身的延遲很小。** 畫面變動時，新影格從顯示器合成完成到 distributor 畫出平均 6 ms（Pixel 7a）／9 ms（A21s）；H.264 編碼每張 7／11 ms；`vision` 取影格的複製 1.4–5 ms。腳本開始後第一張影格要 50–70 ms（Pixel 7a）／115–135 ms（A21s），在那之前 `vision.find` 直接回傳 `nil`。
5. **注入一次點擊只要 0.7 ms（Pixel 7a）／2.4 ms（A21s），相較之下網路來回是 53 ms（Pixel 7a，Wi-Fi）。**
6. **鏡像實體螢幕本身幾乎沒有負擔；負擔來自有消費者時的空轉重畫與編碼。** 只開鏡像、沒有消費者時，行程 CPU 0.3–0.8%；加上 H.264 編碼後 56–62%。

## 對三個決策的建議

| # | 決策 | 建議 | 依據 |
|---|---|---|---|
| C1 | 動態 fps | **先做「有新影格才畫」**：`updateTexImage` 後比對 `getTimestamp()`，沒有變就不 `drawFrame`、不送進 sink；再依 sink 需求限速（編碼器 30 fps）。這是修正而非新功能，預期能消掉靜止畫面約 50% 的常駐 CPU、`vision.wait` 不設 `step_ms` 時的重複比對，以及編碼器 2–3 倍的多餘影格與位元率。之後是否還要「動態 fps」，再以修正後的數字決定 | 結論 1 |
| C2 | mirror VD 自動管理 | **可以做，但排在 C1 之後。** 鏡像本身沒有消費者時幾乎不花資源，自動開關的成本不在鏡像，而在消費者造成的重畫；C1 修好後，開著鏡像的代價會再下降 | 結論 6 |
| C3 | 從 VS Code 注入點擊 | **體感延遲的來源是網路與串流，不是注入。** 注入 < 3 ms，網路來回 53 ms（p90 96 ms），影格到顯示（A6）尚未量測。要做這項功能，先量 A6，並優先處理 C1（編碼器收到的多餘影格會佔用網路頻寬） | 結論 4、5 |

另外兩項與決策無關、但值得另開 issue 的發現：

- `docs/lua-api.md` 可以明說「彩色比對是灰階的 3–4 倍、耗時由搜尋範圍決定」，並建議 `roi` 與 `gray`；低階機上全畫面彩色比對一次要 1–4 秒。
- 腳本開始的前 50–135 ms 沒有影格，`vision.find` 會回傳 `nil`。範例與文件應以 `vision.wait` 開頭，或由引擎在第一次呼叫時等第一張影格。

- Pixel 7a 的 32 px 全畫面樣本數少（1–5），是因為那幾次呼叫落在第一張影格到達之前（見三）。

## 二、OCR（A2）

puppet 畫一行 `LEVEL 12 SCORE 3450 START`，720×1280。執行緒數 A21s 4、Pixel 7a 2（選型研究的最佳值）。

| 呼叫 | 區域 | A21s 偵測／辨識／合計 | Pixel 7a 偵測／辨識／合計 |
|---|---|---|---|
| `vision.read` | 720×160 | —／122／122 | —／19／19 |
| `vision.read_lines` | 720×1280 | 1227／381／1631 | 254／88／344 |
| `vision.find{text}` | 720×1280 | 1198／371／1570 | 280／89／368 |

A21s 與選型研究（`docs/research/ocr-engine-selection.md`）的 ROI 80 ms／整張 2.3 s 同一量級。Pixel 7a 的整張辨識比選型時的 1.1 s 快，原因是畫面上只有一行字：偵測的耗時固定，辨識隨行數線性增加。

## 三、影格管線（A4、A5）

### GLES distributor

| 項目 | A21s | Pixel 7a |
|---|---|---|
| 有 sink 時的重畫次數 | 82 次／秒 | 85 次／秒 |
| 畫面靜止時的新影格 | 0.6 張／秒 | 0 張／秒 |
| 每次重畫（sink 為 vision 的影格讀取／H.264 編碼器） | 1.7／3.3 ms | 1.4／1.0 ms |
| 畫面變動（30 fps）時，新影格合成完成到畫出 | 平均 8.8、最大 16–22 | 平均 6.0、最大 11–12 |
| 沒有 sink 時 | 每 250 ms 醒來一次，不畫 | 同左 |

`GlesDistributor.cpp` 的 render loop 以 `frameCond.wait_for(10 ms)` 驅動，`onFrameAvailable` 沒有接上，所以不論有沒有新影格都會重畫並送到每個 sink。

### H.264 編碼

`H264EncoderSink` 設定 2 Mbps、30 fps、低延遲模式。`編碼` 為影格進編碼器（`presentationTimeUs`）到拿到輸出 buffer 的時間。

| 情境 | A21s fps／編碼／位元率 | Pixel 7a fps／編碼／位元率 |
|---|---|---|
| VD 720×1280，畫面靜止 | 71／11.0／84 kbps | 87／7.7／40 kbps |
| VD 720×1280，30 fps 變動 | 71／10.7／200 kbps | 88／6.9／128 kbps |
| 鏡像實體螢幕（主畫面） | 68／11.8／2.5 Mbps | 86／8.8／7.8 Mbps |

編碼器收到的影格數由 distributor 的重畫次數決定，與內容是否變動無關。實體螢幕的位元率高於設定值，是因為編碼器以 30 fps 分配位元，實際卻收到 2–3 倍的影格。

## 四、輪詢成本（A3）

`vision.wait` 等一個不存在的 64 px 模板，ROI 200×200，畫面靜止，各跑 20 秒，量測試行程的 CPU。

| `step_ms` | A21s | Pixel 7a |
|---|---|---|
| 不設 | 263% | 236% |
| 100 | 125% | 113% |
| 500 | 62% | 54% |
| 1000 | 57% | 52% |

不設 `step_ms` 時，A21s 20 秒內比對 770 次（每次 36 ms），也就是每次重畫都比對一次。`step_ms = 1000` 時剩下的約 50% 是 distributor 本身的重畫。

## 五、輸入回程（A7）

| 項目 | A21s | Pixel 7a |
|---|---|---|
| `injectMotionEvent` 一次點擊（down＋up），50 次 | 2.4／4.9（最大 9.6） | 0.7／1.1（最大 5.8） |
| 電腦到裝置 `GET /health` 來回，50 次 | 未量（見下） | 53／96（最大 1239） |

電腦以 Wi-Fi 連到同一個 AP（計畫原訂有線連接，實際環境沒有）。A21s 的腳本工作台當時沒有在 8787 回應，未量到網路來回。

## 未量測與限制

- A6（影格送到 VS Code 面板顯示的時間）依計畫延後，等要做「從 VS Code 注入點擊」時再量。
- 除 template matching 外各項只有 1 輪；template matching 的 p50 與 p90 差距在 10% 以內，其他項目的數字可視為量級。
- 電池溫度在量測期間為 33–37°C；沒有量測 CPU 頻率，降頻的影響未排除。
- `GlesDistributor` 的 GPU 時間未量，表中「每次重畫」是 CPU 端呼叫 `drawFrame` 的時間。
